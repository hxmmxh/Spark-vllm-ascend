# Spark 部署与使用

**中文** | [English](SKILL.en.md)

使用本仓库的脚本在目标 Ascend 950 主机上完成部署，以实际对话请求验证服务。默认目标为日常使用；用户要求性能测试时再执行三轮测速。

## 确定环境与入口

- 从用户给定路径或当前工作区定位仓库，核对 `pyproject.toml` 中的项目名为 `spark-vllm-ascend`。以下路径均相对仓库根目录；若技能被单独复制，先定位完整仓库，再读取相应文档。
- 执行操作需要能读取仓库并在目标主机运行终端命令。仅有仓库链接时可先阅读文档；缺少目标主机访问或设备时，说明缺失条件，不报告部署成功。
- 阅读[部署要求](../../deployment/README.md)，通过 `uname -m`、`npu-smi info` 和构建工具检查确定实际环境。按 CPU 架构与 NPU 型号选择对应指南：

| 主机与 NPU | 配置 | 指南 |
|---|---|---|
| x86_64 + Ascend950PR_957b | `x86-950pr` | [x86 部署](../../deployment/x86-950pr.md) |
| aarch64 + Ascend950DT_9581 | `arm64-950dt` | [ARM 部署](../../deployment/arm64-950dt.md) |

沿用用户指定的设备、路径和端口；未指定时选取空闲物理 NPU、独立目录和可用端口。指南中的设备编号是示例，不能直接假定可用。使用配置文件选择 SOC 与锁定依赖，不根据 CPU 架构猜测 NPU 型号。

## 执行部署或恢复

阅读[公共部署步骤](../../deployment/common.md)，按当前任务执行对应阶段，具体命令以文档和仓库脚本为准。

- **首次部署**：设置平台指南中的 `BASE`、`PROFILE`、`REPO`、`WORK`、`DEVICE`、`PORT`，完成公共步骤第 1–4 步。通过 uv 创建 `$WORK/.venv`，生成部署副本，安装框架、准备模型、编译算子并执行设备自检。
- **已有环境启动**：定位原部署副本与工作目录，恢复变量和 `run` 函数，核对 `deployment-profile.json`、`python-environment.json` 及自检记录；环境完整时直接进入第 6 步。不要重新执行首次部署中要求目录不存在的检查，也不要覆盖已有环境或权重。
- **恢复安装**：先读失败阶段的日志，再按公共文档的“失败恢复与复测”处理，只重跑需要恢复的阶段及其后续验证。保持已有源码、依赖锁和已完成阶段的记录。

安装、编译、服务和测试使用同一 uv 环境；设备命令经部署副本的 `run_user.sh` 执行。让脚本管理 CANN/NNAL、Triton 后端、通信目录和代理设置，不绕过脚本改用系统 Python 或裸 `vllm serve`。沿用仓库的依赖安装顺序及下载校验。

以日志中的 `RUNTIME_IMPORTS_PASS`、`MODEL_PREPARED 290`、`HEAD_CPU_EXACT`、`HEAD_STRICT_PASS`、`SLOT4_STRICT_PASS` 等对应阶段结果判断完成情况。遇到下载校验不一致、平台不受支持或自检失败，停止依赖该结果的后续步骤，保留日志并报告具体原因，不修改锁文件或跳过检查来继续。

## 启动与验证

按公共步骤第 6 节，在可保持运行的终端会话中启动服务，并在另一终端验证：

1. 使用实际 `PORT` 请求 `/health`，等待 HTTP 200，启动期间检查 `$RUN_OUT/server.log`。
2. 按[日常使用](../../../README.md#日常使用)发送 `/v1/chat/completions` 请求，模型名为 `spark`；确认实际收到有效回复，不能仅凭进程存在判断服务可用。本机 curl 请求使用文档中的 `--noproxy 127.0.0.1`。
3. 根据用户需要给出流式、多轮对话或 SSH 转发用法。默认服务监听 `127.0.0.1`，远程客户端使用文档中的转发方式。

用户要求性能测试时，按第 5 步运行三轮测速及 `verify_results.py`，检查结果报告中的 `complete=true`。测速期间不并行运行第 6 步的服务；完成测速后按用户需求启动日常服务。
